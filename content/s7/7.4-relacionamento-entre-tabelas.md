## Chaves e diagrama ER

- **PK (chave primária):** o "CPF" de cada linha. Nunca repete, nunca fica vazia.
- **FK (chave estrangeira):** uma coluna que guarda a PK de **outra** tabela. Pode repetir. O `author_id` é PK em `author` e FK em `books`.

O **diagrama ER** (entidade-relacionamento) é o mapa dessas ligações: cada caixa é uma tabela (nome no topo, colunas embaixo, PK marcada com chave 🔑), e as linhas mostram quem se liga a quem. "Pé de galinha" na ponta da linha = lado "muitos".

| Relacionamento | Exemplo | Como se monta |
|---|---|---|
| Um para um | Funcionário ↔ conta de pagamento | Raro; separa dados sensíveis |
| Um para muitos | Um autor → vários livros | A FK fica no lado "muitos" (books) |
| Muitos para muitos | Livros ↔ autores; lojas ↔ produtos | Precisa de uma **tabela no meio** (`products_stores`) |

Desenhar o banco é trabalho do engenheiro de dados. O analista lê o diagrama para achar onde está cada informação.

> [!ex] Por que dividir as tabelas
> Na `products_data_all`, o nome e a categoria de cada produto se repetiam em toda linha. Dividido: `products` (cada produto uma vez), `stores` (cada loja uma vez) e `products_stores` (só o que muda: o preço em cada loja e data). A PK de `products_stores` é composta: `id_product + id_store + date_upd`.

## Deduzindo uma ligação

Nem toda ligação aparece como linha no diagrama. Para "quanto o cliente pagou numa compra?":

1. O que eu quero? O preço, que só existe em `products_stores`.
2. O que eu tenho? `transactions`: produto, loja e data.
3. Tem linha ligando as duas? Não.
4. Quais colunas têm o **mesmo significado** nas duas? Produto, loja e data (com nomes diferentes: `date` e `date_upd`).
5. O formato bate? `date` tem hora da compra (14:37); `date_upd` tem hora da coleta (08:00). Converta as duas para dia: `::date`.
6. Teste com um caso e confira se a quantidade de linhas não mudou.

```sql
FROM transactions
LEFT JOIN products_stores
  ON products_stores.id_product = transactions.id_product
 AND products_stores.id_store   = transactions.id_store
 AND products_stores.date_upd::date = transactions.date::date
```

> [!erro] Ligação deduzida pode falhar
> Sem coleta de preço no dia, a compra fica sem preço. Com duas coletas no dia, a compra aparece **duas vezes** e a soma infla. Conte as linhas antes e depois do JOIN.

## INNER JOIN

Junta duas tabelas pela coluna em comum e traz **só as linhas que têm par nos dois lados** (a interseção).

```sql
SELECT books.name, author.first_name, author.last_name
FROM books
INNER JOIN author ON author.author_id = books.author_id;
```

- `ON` diz a regra da ligação.
- `tabela.coluna`: as duas têm `author_id`, então o SQL precisa saber de qual.
- No INNER a ordem das tabelas não muda o resultado.
- Apelidos ajudam: `FROM books AS b JOIN author AS a ON a.author_id = b.author_id`.

> [!erro] JOIN pode multiplicar linhas
> Se um id aparece duas vezes do outro lado, a linha da esquerda aparece duas vezes. Somar depois conta em dobro. Para contar compras depois de um JOIN que repetiu linhas: `COUNT(DISTINCT id_transaction)`. Se as linhas repetidas forem 100% iguais, `SELECT DISTINCT` resolve.

## LEFT JOIN e RIGHT JOIN

| JOIN | Traz |
|---|---|
| `INNER` | Só quem tem par nos dois lados |
| `LEFT` | **Toda** a tabela do `FROM` (esquerda) + o par da direita, se houver; sem par vira `NULL` |
| `RIGHT` | **Toda** a tabela do `JOIN` (direita) + o par da esquerda |

```desenho joins-venn
```

```sql
SELECT ...
FROM author                 -- ESQUERDA: vem inteira
LEFT JOIN books             -- DIREITA
  ON books.author_id = author.author_id;
```

`author LEFT JOIN books` → 33 linhas: todos os autores, os sem livro com `NULL`. `books LEFT JOIN author` → 30 linhas: um por livro. **No LEFT e no RIGHT, a ordem importa.**

`A RIGHT JOIN B` é o mesmo que `B LEFT JOIN A`. No mercado quase todo mundo usa só o LEFT, deixando a tabela principal no `FROM`.

> [!dica] Qual tabela vai no FROM?
> Pergunte: "de qual tabela eu preciso de **todas** as linhas?". Ela vai no `FROM`, e a outra no `LEFT JOIN`.

## Achando o que falta: LEFT JOIN + IS NULL

```sql
-- produtos que nunca foram vendidos na loja 3
SELECT DISTINCT products.name
FROM products
LEFT JOIN (SELECT DISTINCT id_product
           FROM transactions
           WHERE id_store = 3) AS subquery
  ON subquery.id_product = products.id_product
WHERE subquery.id_product IS NULL;
```

Quem ficou com `NULL` do lado direito é quem não tem par. No dia a dia: clientes que nunca compraram, produtos sem venda no mês, pedidos sem pagamento.

## Vários JOINs

Cada JOIN traz mais uma tabela para dentro do resultado, de cima para baixo:

```sql
SELECT books.name, author.last_name, genre.name AS genre_name
FROM books
INNER JOIN author ON author.author_id = books.author_id
INNER JOIN genre  ON genre.genre_id   = books.genre_id;
```

> [!erro] INNER depois de LEFT apaga os NULL
> `genre LEFT JOIN books` trouxe gêneros sem livro (com `author_id` NULL). Um `INNER JOIN author` em seguida não acha par para NULL e remove essas linhas. Para manter tudo de uma tabela, use LEFT em todos os JOINs seguintes.

## JOIN + agregação

O JOIN acontece antes de tudo, então dá para agrupar por uma coluna de uma tabela e contar outra de outra:

```sql
SELECT genre.name AS genre_name, COUNT(books.name) AS name_cnt
FROM books
INNER JOIN genre ON genre.genre_id = books.genre_id
GROUP BY genre.name;
```

> [!comp] Condição no ON × no WHERE (com LEFT JOIN)
> - `LEFT JOIN books ON ... AND books.pages > 900`: **todos** os autores ficam; quem não tem livro de mais de 900 páginas fica com NULL (16 linhas).
> - `LEFT JOIN books ON ... WHERE books.pages > 900`: o WHERE roda depois e tira os NULL (3 linhas).

## UNION e UNION ALL

O JOIN cola tabelas **lado a lado** (mais colunas). O UNION **empilha** uma embaixo da outra (mais linhas), sem precisar de chave.

```sql
SELECT year_tag, name, weight FROM cows_grandpa
UNION                       -- ou UNION ALL
SELECT tag, name, weight FROM cows_grandma;
```

| | UNION | UNION ALL |
|---|---|---|
| Linhas repetidas | Remove (iguais em **todas** as colunas) | Mantém |
| Velocidade | Mais lento | Mais rápido |
| Use quando | Quer contar cada item uma vez | Sabe que não há repetição, ou a repetição importa (vendas de janeiro + fevereiro) |

Regras: mesma quantidade de colunas, na mesma ordem, com tipos compatíveis. Os nomes vêm do primeiro SELECT. Cuidado: duas colunas de texto em ordem trocada (`name, breed` e `breed, name`) não dão erro e embaralham os dados.

Para contar depois do UNION, coloque-o numa subconsulta: `SELECT COUNT(sub.name) FROM (... UNION ...) AS sub;` (o `;` só no final de tudo).

> [!ver] Ver também
> O mesmo raciocínio de junções no pandas: `merge` com `how='inner'/'left'/'right'/'outer'` em [3.7](#c3-7). `concat` é o UNION ALL do pandas.

## NULL e CASE

`NULL` é a célula vazia: "não sei o valor". Não é zero nem texto vazio.

```sql
WHERE publisher_id IS NULL        -- as vazias
WHERE publisher_id IS NOT NULL    -- as preenchidas
```

> [!erro] Com NULL, nunca use =
> `WHERE publisher_id = NULL` não dá erro, mas devolve 0 linhas: "não sei = não sei" não é verdadeiro. Sempre `IS NULL`. `COUNT(*) - COUNT(col)` dá quantos vazios a coluna tem.

**CASE** é o `if / elif / else` do SQL:

```sql
SELECT name, pages,
  CASE WHEN pages >= 1000 THEN 'gigante'
       WHEN pages >= 500  THEN 'longo'
       ELSE 'curto'
  END AS tamanho
FROM books;
```

- Testa os `WHEN` de cima para baixo e para no primeiro verdadeiro (a ordem importa).
- Sem `ELSE`, o que não bateu vira NULL.
- Todos os resultados precisam ser do mesmo tipo.
- `COALESCE(publisher_id, -1)`: devolve o primeiro valor não NULL. Atalho para "trocar NULL por X".

## LIKE

Procura um pedaço de texto (o Ctrl + F do SQL):

| Curinga | Significa | Exemplo |
|---|---|---|
| `%` | Qualquer quantidade de caracteres (até zero) | `'%Vampire%'`, `'The%'`, `'%s'` |
| `_` | Exatamente um caractere | `'__'` = 2 caracteres |

- `LIKE` diferencia maiúsculas; `ILIKE` (PostgreSQL) não.
- `NOT LIKE` pega o que não tem o padrão.
- Para buscar o próprio `%`: `WHERE name LIKE '%1!%%' ESCAPE '!'` (o `!` avisa que o próximo símbolo é literal).
