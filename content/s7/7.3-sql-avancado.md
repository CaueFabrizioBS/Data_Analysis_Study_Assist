## GROUP BY

Calcula uma agregação **para cada grupo**, como o `groupby` do pandas.

```sql
SELECT author, COUNT(name) AS cnt
FROM books
GROUP BY author;
```

```python
books.groupby('author')['name'].count()      # mesma coisa no pandas
```

Várias colunas: `GROUP BY author, genre` (cada combinação vira um grupo). Várias funções: separe por vírgula no `SELECT`.

> [!regra] As duas regras de ouro
> 1. Toda coluna solta no `SELECT` (fora de função) tem que estar no `GROUP BY`. Atalho: copie tudo do SELECT para o GROUP BY, menos as funções.
> 2. Função de agregação nunca vai dentro do `GROUP BY`.

## ORDER BY, LIMIT e HAVING

```sql
SELECT author, COUNT(name) AS name_cnt
FROM books
WHERE pages > 500                 -- 1º filtra LINHAS
GROUP BY author
HAVING COUNT(name) > 1            -- 2º filtra GRUPOS
ORDER BY name_cnt DESC, author    -- ordena (desempate pelo nome)
LIMIT 3;                          -- só as 3 primeiras
```

- `ORDER BY` é crescente (`ASC`) por padrão; `DESC` vem logo depois da coluna.
- `LIMIT` sem `ORDER BY` pega linhas em qualquer ordem. Com `ORDER BY ... DESC`, vira um "top N".

| | WHERE | HAVING |
|---|---|---|
| Filtra | Linhas, **antes** de agrupar | Grupos, **depois** de agrupar |
| Usa | Colunas da tabela | Resultado de funções (`COUNT(name) > 1`) |
| `COUNT()` dentro | Erro | É para isso que ele serve |

Quando os dois funcionam (filtro numa coluna do GROUP BY), prefira `WHERE`: sobra menos coisa para agrupar.

## Ordem de execução

Você **escreve** numa ordem, o banco **executa** em outra:

```desenho ordem-execucao-sql
```

```fluxo
FROM / JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT
```

> [!erro] Apelido no WHERE ou no HAVING
> O apelido (`AS name_cnt`) nasce no `SELECT`, que roda **depois** do WHERE e do HAVING. Lá ele ainda não existe: repita a expressão (`HAVING COUNT(name) > 1`). No `ORDER BY` o apelido funciona.

## Datas: EXTRACT e DATE_TRUNC

| | `EXTRACT(MONTH FROM log_on)` | `DATE_TRUNC('month', log_on)` |
|---|---|---|
| Faz | Recorta **uma peça** | Corta tudo **abaixo** do nível |
| `2019-03-25 14:30:46` vira | `3` (um número) | `2019-03-01 00:00:00` (uma data) |
| Escrita | Peça sem aspas, separada por `FROM` | Nível entre aspas, separado por vírgula |
| Use para | Comparar "dia 1 × dia 15", "segunda × sábado" | Linha do tempo, agrupar por mês/semana/hora |

Peças do `EXTRACT`: `YEAR`, `QUARTER`, `MONTH`, `WEEK`, `DAY`, `DOY` (dia do ano), `ISODOW` (segunda = 1, domingo = 7), `HOUR`, `MINUTE`.

Níveis do `DATE_TRUNC`: `'year'`, `'quarter'`, `'month'`, `'week'` (volta para a segunda), `'day'`, `'hour'`, `'minute'`...

> [!erro] A anomalia do dia 1
> Compras de 1º de junho a 1º de julho. `GROUP BY EXTRACT(DAY ...)` mostrou o dia 1 com quase o dobro dos outros (1989). Não era pico: o EXTRACT juntou **1º de junho** (961) e **1º de julho** (1028) no mesmo grupo. Com `DATE_TRUNC('day', ...)` cada data fica separada. Resultado estranho é motivo para investigar, não para concluir.

Data guardada como texto: converta antes (`date_upd::timestamp`).

| SQL | pandas |
|---|---|
| `EXTRACT(MONTH FROM col)` | `df['col'].dt.month` |
| `DATE_TRUNC('hour', col)` | `df['col'].dt.floor('h')` |
| `DATE_TRUNC('month', col)` | `df['col'].dt.to_period('M')` |

## Subconsultas

Uma consulta dentro de outra. Leia **de dentro para fora**.

| Onde | Vira | Regra |
|---|---|---|
| `FROM (...) AS sub` | Uma tabela | Precisa de nome; chame as colunas como `sub.coluna` |
| `WHERE col = (...)` | Um valor | A interna devolve 1 linha só |
| `WHERE col IN (...)` | Uma lista | Várias linhas, mas 1 coluna só |

```sql
-- média de avaliações por gênero: função dentro de função não pode,
-- então conta numa consulta e tira a média na outra
SELECT AVG(sub.count_rating) AS avg_count_rating
FROM (SELECT COUNT(rating) AS count_rating
      FROM books
      GROUP BY genre) AS sub;

-- livros acima da média de páginas
SELECT name, pages
FROM books
WHERE pages > (SELECT AVG(pages) FROM books);

-- livros de 3 editoras pelo nome (a tabela books só tem o id)
SELECT name FROM books
WHERE publisher_id IN (SELECT publisher_id FROM publisher
                       WHERE name IN ('Knopf', 'Collins', 'Crown'));
```

> [!erro] Subconsulta com =
> Se a interna devolve mais de uma linha, `=` dá erro ("more than one row returned"). Use `IN`.

## Funções de janela (OVER)

Calculam uma agregação **sem juntar as linhas**: o resultado aparece ao lado de cada linha.

```desenho group-vs-over
```

```sql
SELECT author_id, name, price,
       price / SUM(price) OVER (PARTITION BY author_id) AS ratio
FROM books_price;
```

| | GROUP BY | OVER |
|---|---|---|
| Linhas no resultado | Uma por grupo | Todas continuam |
| Outras colunas no SELECT | Precisam estar no GROUP BY | Livres |

Anatomia: `FUNÇÃO() OVER (PARTITION BY ... ORDER BY ... ROWS BETWEEN ...)`. Tudo dentro do `OVER` é opcional; `OVER ()` vazio usa a tabela toda.

| Parte | Responde | Exemplo |
|---|---|---|
| `PARTITION BY` | Quais grupos? (o "por" do enunciado) | "do autor" → `PARTITION BY author_id` |
| `ORDER BY` | Em que ordem percorrer? | `ORDER BY date_pub` |
| `ROWS BETWEEN` | Quantas linhas entram na conta? | `UNBOUNDED PRECEDING AND CURRENT ROW` |

**Soma acumulada:**

```sql
SUM(pages) OVER (PARTITION BY author_id ORDER BY date_pub
                 ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)
```

`PRECEDING` = linhas acima, `FOLLOWING` = abaixo, `UNBOUNDED` = até a borda, `CURRENT ROW` = a atual. `ROWS BETWEEN 1 PRECEDING AND CURRENT ROW` é uma janela móvel de 2 linhas.

**Funções que só existem com OVER** (precisam de `ORDER BY` dentro):

| Função | Faz |
|---|---|
| `RANK()` | Posição no grupo; empate divide a posição e **pula** a próxima (1, 1, 3) |
| `DENSE_RANK()` | Empate não pula (1, 1, 2) |
| `ROW_NUMBER()` | Nunca empata (1, 2, 3) |
| `NTILE(n)` | Divide em n faixas com a mesma **quantidade** de linhas (não pelo valor) |
| `LAG(col)` / `LEAD(col)` | Valor da linha de cima / de baixo. O primeiro `LAG` é `NULL` |

```sql
receita - LAG(receita) OVER (ORDER BY mes) AS diferenca   -- variação mês a mês
```

> [!erro] Janela no WHERE
> A janela roda junto com o `SELECT`, depois do `WHERE`. Por isso `WHERE SUM(price) OVER (...) > 10` dá erro. Para filtrar pelo resultado, coloque a consulta numa subconsulta e filtre por fora. E a janela só enxerga as linhas que sobraram do `WHERE`.

> [!ex] Os dois ORDER BY
> O `ORDER BY` de **dentro** do OVER define a ordem da conta. O de **fora** define a ordem em que as linhas aparecem no resultado.

## Traduzindo o enunciado

| Se o enunciado diz | Vira |
|---|---|
| "o número de", "quantos" | `COUNT()` |
| "únicos", "diferentes" | `COUNT(DISTINCT col)` |
| "o total", "a soma" | `SUM()` |
| "a média" | `AVG()` |
| "o maior", "o menor" | `MAX()` / `MIN()` |
| "por dia", "para cada loja" | `GROUP BY` |
| "que custam mais de" | `WHERE` |
| "cujo total seja maior que" | `HAVING` |
| "nomeie como" | `AS` |
| "os 5 maiores" | `ORDER BY ... DESC LIMIT 5` |

> [!dica] O truque do "por"
> O que vem depois do "por" é a **caixa** (GROUP BY). O que você quer saber de cada caixa é a **conta** (a função). "Número de transações por dia" → `COUNT(id_transaction)` + `GROUP BY dia`.

> [!erro] "Leites e manteigas" é OR
> Em português, "e" junta as listas. O WHERE olha **uma linha por vez**, e nenhum produto é leite e manteiga ao mesmo tempo:
> `WHERE (category = 'milk' AND price > 17) OR (category = 'butter' AND price > 9)`

**Checklist de erros que já apareceram:**

- Vírgula entre condições do WHERE (use AND/OR).
- Apelido no WHERE ou HAVING.
- Coluna solta no SELECT fora do GROUP BY.
- `DISTINCT col` sozinho quando o enunciado pede "número de" (é `COUNT(DISTINCT col)`).
- Subconsulta de várias linhas com `=` (use IN).
- Data guardada como texto (converta com `::date` ou `::timestamp`).
